# COMPASS P0 — profile, calendar and chat security runbook

Status: implementation ready for independent review; production execution is
intentionally not performed from this branch.

## Scope and safety boundary

This change is an `expand` release. It applies C0 and C1 only:

1. anonymous profile reads are removed immediately;
2. authenticated cross-user profile reads remain temporarily for application
   compatibility;
3. self-service changes of role, HR/finance, system status, consent, avatar/CV,
   embedding, onboarding, streak and loyalty fields are blocked in the database;
4. the three privileged lifecycle/delete RPCs are service-role-only and have an
   internal JWT-role check;
5. a minimal `profile_directory` is introduced;
6. calendar feeds use opaque, hash-only tokens;
7. chat attachments move to a private bucket and guarded server actions.

The C2 contract migration is deliberately **not** included. Direct authenticated
profile writes and the broad compatibility read can be removed only after all
remaining application callers are migrated and the role matrix is green.

## Verification

Run against an isolated environment first. Never paste production keys into a
terminal transcript or CI log.

```sql
-- Anonymous profile access must be absent.
select has_table_privilege('anon', 'public.profiles', 'select');

-- Temporary expand compatibility remains until C2.
select has_table_privilege('authenticated', 'public.profiles', 'select');

-- Client roles cannot execute privileged RPCs.
select
  has_function_privilege('anon', 'public.admin_hard_delete_user(uuid)', 'execute'),
  has_function_privilege('authenticated', 'public.admin_hard_delete_user(uuid)', 'execute');

-- Bucket is private and constrained.
select id, public, file_size_limit, allowed_mime_types
from storage.buckets
where id = 'chat-attachments';
```

Expected results: `false`, `true`, both RPC values `false`, and a private bucket
with a 10 MB limit plus only JPG/PNG/WEBP/PDF/TXT MIME types.

Application scenarios:

- anonymous REST `profiles` request is denied;
- a user can update `bio` but cannot update own `role`, `current_status`,
  `employment_status`, `avatar_url`, onboarding, streak or loyalty values;
- `profile_directory` works but contains no email, phone, role, HR or finance;
- a UUID calendar token returns 410;
- malformed, missing, revoked and inactive-account tokens return the same 401;
- rotating a token invalidates the old token immediately;
- a non-participant cannot upload or download a chat attachment;
- allowed participant uploads use
  `{conversation_id}/{user_id}/{uuid}.{ext}` and signed download URLs;
- an unsupported, empty or over-10-MB file is rejected.

## Rollback

This is an expand release. Prefer a forward fix. Do not restore public profile
access or make the chat bucket public merely to roll back the UI.

If the application must be rolled back:

1. keep C0 active;
2. deploy the previous allowed application SHA;
3. keep the temporary authenticated profile-read compatibility policy;
4. disable only the calendar-settings and attachment UI if necessary;
5. do not remove C1 tables/columns while any new release may have written data;
6. ship a reviewed forward fix, then resume the expand/app/contract sequence.

The rollback floor moves past this release only after attachment metadata and
calendar token writes have been observed and the prior app is no longer needed.

## Incident review and DPO decision

Review the period beginning with the earliest exposure date available in logs.
At minimum preserve and inspect:

- Supabase/PostgREST reads of `profiles`, especially anonymous or bulk reads;
- update attempts affecting role, employment, manager, leave, loyalty, status,
  avatar/CV, consent and embedding fields;
- calls to the three privileged RPCs and all user deletion events;
- calendar feed requests, source IP/ASN, user agent, response status and rate;
- Storage reads/writes under `chat-attachments`, including public-object URLs;
- application and Cloudflare request IDs that correlate with these events.

Record: time range, log source, query/hash, reviewer, finding and preservation
location. Do not put raw access tokens or personal data in this repository.

The historical migration
`20260220_create_centrala_user.sql` contains a fixed credential bootstrap. Its
credential must be considered compromised even if the migration was never run.
Verify whether the account exists, preserve its activity, disable/quarantine it
without deleting historical relations, and rotate any reused credential. The
normalized fresh-replay work disables this seed; production reconciliation must
confirm the live state explicitly.

## Known reconciliation blocker

The repository currently has duplicate migration versions and historical schema
drift. A disposable normalized copy was successfully replayed from zero, but
renaming already-applied migrations requires an explicit version mapping and a
production `migration repair` procedure. Do not copy the disposable tree into
production or run ad-hoc MCP DDL. The migration-reconciliation change and its
preflight are a separate reviewed P1 deliverable.
